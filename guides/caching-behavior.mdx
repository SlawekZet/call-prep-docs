## How caching works

CallPrep caches enriched data per `(email, product)` combination.
When you submit a research request for an email that was recently enriched,
we return cached data immediately — no external API calls are made.

This means:

- **Response time drops from ~30s to <2s**
- **No additional data source costs are incurred**
- **A credit is still consumed** per request (you're using the service)

## Cache TTLs

| Data type       | Cache TTL     | Notes                                                           |
| --------------- | ------------- | --------------------------------------------------------------- |
| Prospect data   | 30 days       | Name, title, LinkedIn URL, employment history                   |
| Company data    | 90 days       | Industry, description, tech stack, HQ                           |
| Decision makers | 180 days      | Key people at the company                                       |
| AI insights     | Same as above | Summary, opening talks, synergy points — regenerated if missing |
| LinkedIn posts  | Same as above | Re-fetched if not present in cache                              |

## Granular cache flags

Cache invalidation is granular — we track separately whether each component is fresh:

- **`fetch`** — should we call external APIs for new prospect/company data?
- **`needsAI`** — should we regenerate AI insights?
- **`needsPosts`** — should we re-fetch LinkedIn posts?

This means if a previous research run completed but failed at the AI step,
the next request will **only** regenerate AI insights — without re-calling
Apollo, PDL, or LinkedIn.

## Cache is per product

Cache is scoped to `(email, user, product)`. If you have two API keys
with different product contexts, they each maintain their own cache —
so the same email can be researched twice with different insights.

## Forcing a fresh research

There is currently no way to bypass the cache via the API.
If you need fresh data for a prospect whose cache is still valid,
contact [hello@callprep.app](mailto:hello@callprep.app).

<Tip>
  Cache TTLs are designed to balance freshness with cost. For most sales use
  cases, 30-day prospect data is fresh enough — job titles and companies change
  less frequently than that.
</Tip>

## Cache and retention are different clocks

A cache TTL is how long data is reused instead of looked up again. Retention is
how long it is kept at all — 365 days for prospect and company records, then
deleted. See [Data retention](/plans/data-retention).
